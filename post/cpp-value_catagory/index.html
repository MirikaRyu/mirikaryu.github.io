前言

从接触 C++ 至今都没有比较完整的了解过整个值类别的系统，实际编写代码时基本就是凭感觉使用各种引用，于是就花了点时间简单的 研究了一下相关内容。最后只能说虽然没有想象中的那么复杂，但真的挺恶心人的，有一种处处都在为屎山规则打补丁的感觉。

个人认为 C++ 与值类别相关的混淆完全来源于将值类别和类型这两个毫不相关的概念都通过类型系统（引用）进行表达。

比如经常听到的一句话：“右值引用是左值”，其实是专指像 int&& a = 1; 中 a 这个标识符在作为表达式的时候是左值。但 std::move(x) 返回的也是右值引用类型，难道它还是左值吗？所以在我看来这句话的误导性非常强，因为其实际上暗示了值类别和标识符类型挂钩， 但这是完全不正确的。

因此在下文中我会尽可能的将值类别系统和类型系统分开说明。

值类别

首先有两点必要的认知：

  1. 只有表达式才有值类别这个属性。
  2. 表达式的值类别和类型毫无关联。

还是以经典的 int&& a = 1; 进行说明。首先这是一条带初始化器的声明语句，至少在赋值号左边是没有值类别这个概念的，只能说标识符 a 的类型就是 int&&。而 a; 是一条表达式语句，其表达式的类型是 int，而值类别为左值，合起来就是 int&。

那么 C++ 中有哪些值类别呢？最初 C++ 中值类别的语义也是从 C 中借鉴的，仅简单的分成了左值和右值。 然后为了实现资源重用以及 RVO 之类的优化，最终在 C++17 中演变成了下面这样：

graph TD
    Expr["expression
表达式"] --> Glvalue["glvalue
泛左值"]
    Expr --> Rvalue["rvalue
右值"]

    Glvalue --> Lvalue["lvalue
左值"]
    Glvalue --> Xvalue["xvalue
亡值"]

    Rvalue --> Xvalue
    Rvalue --> Prvalue["prvalue
纯右值"]

    class Expr main;
    class Glvalue,Rvalue sub;
    class Lvalue,Xvalue,Prvalue leaf;

从图中可以得知任何一个表达式都属于 lvalue, xvalue, prvalue 这三类中的一类，而其中 xvalue 同时表现出 glvalue 和 rvalue 的性质。

我们将值类别进行区分的原因肯定是由于不同的类别有不同的性质，而这些性质直接关系到能否将该表达式的值进行复用， 以及能否消除掉不必要的复制以提升性能，所以有必要知道不同值类别之间的差别在什么地方。

除此之外，由于值类别是表达式自身的性质，因此我们只能通过观察其结构来判断该表达式的值类别。也就是必须得记住不同的 patterns 🤪

glvalue / 泛左值

泛左值有如下性质：

  • 泛左值可以通过左值到右值、数组到指针或函数到指针隐式转换转换成纯右值。
  • 泛左值可以是多态的：它标识的对象的动态类型不必是该表达式的静态类型。
  • 泛左值可以具有不完整类型，只要表达式中容许。

是什么意思呢？第一条就是在说这些情况：

int a{};
int b = a;

a + 1;

int arr[8]{};
int* p = arr;

由于变量的初始化以及内建的 + 运算符需要一个纯右值，但无论是 a 还是 arr 作为表达式都是左值，因此这里会发生从左值到纯右值 的隐式转换，而数组和函数与普通变量不同的是会 decay 成纯右值指针。

但是要注意不是所有情况下都能够转换，不然就会出现下面这种魔幻代码：

int a{};
int&& ref = a;  // error

然后剩下两条基本就是字面意思：

// 动态多态，纯右值不可行
struct foo {};
struct bar : foo {};

bar obj{};
foo* p = &obj;

// 不完整类型
struct Dummy;
Dummy dummy;

rvalue / 右值

右值的性质如下：

  • 右值不能由内建的取址运算符取地址：&int()、&i++、&42 及 &std::move(x) 是非法的。
  • 右值不能用作内建赋值运算符及内建复合赋值运算符的左操作数。
  • 当被用作函数实参且该函数有两种重载可用，其中之一接受右值引用的形参而另一个接受 const 的左值引用的形参时，右值将被绑定到右值引用的重载之上（从而，当复制与移动构造函数均可用时，以右值实参将调用它的移动构造函数，复制和移动赋值运算符与此类似）。

前面两个很好理解，总不能写出 &0 或者 1 = 2 这种东西。第三条说的重载决议其实就是说如果有以下重载：

void func(const int&);
void func(int&&);

则 func(1) 会绑定到 void func(int&&)，根据这个机制，在选择构造函数时就可以优先调用一个类型的移动构造函数。

lvalue / 左值

  • 与泛左值相同。
  • 可以通过内建的取址运算符取左值的地址：&++i 及 &std::endl 是合法表达式。
  • 可修改的左值可用作内建赋值和内建复合赋值运算符的左操作数。

将泛左值加上一个名字之后就变成了左值，所以左值除了泛左值的性质外，还可以获取到某个对象具体的地址。这里「可修改的左值」是 来自 C 的措辞，将数组、函数以及被 const 修饰的类型等给排除在外。

那么哪些表达式会被归类为左值呢？大致有以下几类：

  1. 具名的变量、函数、数据成员的名字。这个比较好解释，既然你都具名了，那必然会指代一个具体的内存对象，完全符合左值的定义，当然是 左值，举例说明一下就是：

    int&& a = 1;
int b{};
void func(void);
const int& ref = b;

    以上这些标识符作为表达式的时候全部都是左值。

  2. 感觉上可以被赋值的表达式。这边就包含例如内建赋值运算、内建前缀自增/自减等等一大堆东西，详细的可以去查看 cppreference，比如：

    a += b
++a
*p
a[n]
a.m
p->m

  3. 转换到左值引用类型的转型表达式，以及返回左值引用类型的函数调用表达式：

    std::getline(std::cin, str)
std::cout << 1
static_cast<int&>(x)

    这里面还有一个特例是函数类型，无论怎么操作都是左值。就算函数调用返回的是其右值引用，或者手动转换到右值引用，其依然是左值。

  4. 典中典字符串字面量。C 语言遗留机制，比如 "Hello world"。

  5. 使用左值引用或者类类型的常量模板形参（NTTP）：

    struct dummy {};

template <dummy a, int& b>
void foo(void)
{
    &a; // 左值，可以取地址
    &b; // 左值，可以取地址
}

    需要注意的是，使用标量类型的常量模板形参是纯右值。

💡 提示

位域可以被赋值号赋值，但不能取地址，只能复制并绑定到 const 左值引用或者右值引用，被归类为泛左值。

prvalue / 纯右值

  • 与右值相同。
  • 纯右值不具有多态：它所标识的对象的动态类型始终是该表达式的类型。
  • 非类非数组的纯右值不能有 cv 限定，除非它被实质化以绑定到 cv 限定类型的引用。（注意：函数调用或转型表达式可能生成非类的 cv 限定类型的纯右值，但它的 cv 限定符通常被立即剥除。）
  • 纯右值不能具有不完整类型（除了类型 void，或在 decltype 说明符中使用之外）。
  • 纯右值不能具有抽象类类型或它的数组类型。

相比右值多出来的这几条规则基本就是和泛左值对着干的。先说说多态的问题，动态多态依赖的是查找内存中的虚表，但如果是一个 prvalue，其 压根就不是内存中的对象，没有实体，动态多态自然就无从谈起。

接着来看看第三条规则在说什么，其实挺无聊的：

const int foo(void) { return 0; }
int a = foo();

就是在这个场景下返回值的 const 会被剥离，但为何类类型又是例外？是因为其成员函数可以有 cv 限定：

struct foo
{
    void bar(void);
    void bar(void) const;
};

const foo make_foo(void);

make_foo().bar();

在这个场景下 prvalue 的 cv 限定就是有意义的。

然后来看看哪些结构是纯右值：

  1. 字面量（字符串除外）和枚举值（包含成员枚举值）。不用多说了，例如 42, nullptr 等。

  2. 各种看起来像纯右值的东西，包含了各种算术运算和概念相关的表达式：

    i++
a + b
&a
this
requires (T a, T b) { { a + b}; }
std::same_as<T, int>

    这里可以说明的地方是未决成员函数调用这个例外：

    struct foo
{
    void func(void);
    void func(int);
};

foo obj{};
void (foo::*pmf)(int) = &foo::func;

// 这些表达式是未决成员函数调用
obj.func
obj.*pmf

    未决成员函数调用虽然也是纯右值，但只能拿来填入实参后调用函数，像 (obj.*pmf)(1);，甚至不能拿来绑定引用。

    void 和 throw 表达式跟这个类似，会有一些限制，不过不太重要就不再展开了。 更详细的说明同样参考 cppreference。

  3. 转换到非引用类型的转型表达式，以及返回非引用类型的函数调用表达式：

    str.substr(1, 2)
str1 + str2
static_cast<double>(x)
std::string{"Hello world"}

  4. 使用标量类型的常量模板形参（NTTP）：

    template <int a>
void foo(void)
{
    // &a;
    // prvalue，无法取地址
}

  5. lambda 表达式，例如 [] { return 1; }。
    关于这个有一段之前看到的有趣代码：

    int main(void)
{
    [](this auto &&self) -> void
    {
        static int count = 3;

        if (count > 0)
        {
            std::print("{}", count--);
            self();
        }
    }();
}

    可以想想为何上面这个程序的输出为 3321 而不是 321？

xvalue / 亡值

  • 与右值相同。
  • 与泛左值相同。

亡值的性质其实就是右值和泛左值性质的并集，但单拿出来看是没什么作用的，其真正的价值是作为左值和右值之间的桥梁， 这要在后面绑定引用以及选择重载函数的时候才能够体现出来。

亡值主要有以下这几类：

  1. 转换到右值引用类型的转型表达式，以及返回右值引用类型的函数调用表达式：

    std::move(vec)
static_cast<int&&>(a)

    这应该是我们最熟悉也是最典型的用法了，用于将一个左值转换为亡值。

  2. 对已有的右值进行的操作，比如成员访问和下标访问：

    a.m
a.*mp
a[n]

    至于为什么可以包含纯右值请继续往下看。

  3. 具有「移动资格」的表达式。
    这是个什么东西呢？简单来说就是有一个左值表达式，指代了非 volatile 限定的自动存储期局部变量， 然后跟在 return, co_return 以及 throw 后面，比如：

    auto func(void)
{
    std::vector<int> x{};
    return x;
}

    显然这个规则是为了返回值优化准备的，这样可以尽可能的进行移动而不是拷贝，详情可以查看 RVO 这个小节。

上面所有的这些简化规则其实已经基本涵盖了「值类别」本身的内容，虽然已经有点复杂了，但还算清晰，不至于引发混淆或混乱。 只有当这些规则和类型系统、模板等其它功能交互时才是邪恶的开端 😈。

引用、临时量与模板

先说引用绑定的规则，这里是个人感觉有点容易混淆的地方，但有了前面的分类后其实也比较清晰：

引用类型能够绑定的值类别
左值引用 int&左值
右值引用 int&&右值（亡值、纯右值）
只读左值引用 const int&所有值类别（左值、亡值、纯右值）

当函数返回引用以及将引用作为函数参数的时候也适用同样的规则。作为返回类型时，引用绑定的是 return 后的表达式；作为函数形参时， 绑定的是调用方传入的实参，不同的引用类型可以参与重载决议，比如当匹配右值的时候右值引用 int&& 的优先级 高于只读左值引用 const int&。

但这样又会引出一个新问题，在以下代码中：

int&& a = 1;
const int& b = 1;

const auto& c = []{ return std::string{"Hello"}; }();

当这三个引用绑定 prvalue 的时候，其绑定的究竟是什么？我们知道从 C++17 开始，prvalue 就是一个没有实体的幽灵， 但显然以上的 a, b, c 均为左值表达式，说明其指代的一定是一个在内存中的对象。临时量实质化就是用来解决这个矛盾的。 补丁+1

临时量实质化的作用是将任何完整类型 T 的 prvalue 转换为同类型的 xvalue， 这个过程中会产生一个以该 prvalue 初始化的临时对象。简单来说就是将 prvalue 这个字面量找了块实际的内存存放并开始其生命周期。

这个过程会在以下常见场景发生：

  1. 绑定引用到纯右值的时候，如上所示。

  2. 访问纯右值类的数据成员（包含调用 callable 对象），例如：

    struct foo { int m; };
int a = foo{}.m;

  3. 纯右值数组取下标或转换为指针时。

    int* p = std::type_identity_t<int[]>{1, 2, 3};      // Bad, p is dangling
int  n = std::type_identity_t<int[]>{1, 2, 3}[1];   // OK

完整的场景请查看 cppreference。

💡 提示

这种情况没有发生临时量实质化：

int a = 1;
auto str = std::string{"Hello"};

这里 prvalue 会直接在结果对象中构造，这是由 C++17 的语言规则强制保证的。

然后让我们继续仔细观察上面几个例子，又会发现一个新问题：生成的临时对象的生命周期是怎样的？比如对于 const int& a = 1;， 如果 a 绑定到临时对象但该对象在这行语句结束后就失效了，那不直接炸了。所以单独有临时量实质化是不够的， 还需要另外的规则来扩展其生存期。

一旦引用被绑定到临时对象或它的子对象，临时对象的生存期就被延续以匹配引用的生存期，除了以下特例，到底有多少特例啊喂 😡：

  1. 临时对象绑定到函数形参或 new 出来的对象中的引用成员时，其生命周期仅限当前表达式。也就是像这样：

    int&& ref = std::move(1);

struct foo { const int& r; };
foo* p = new foo{1};

    ref, p->r 都是悬垂引用。

  2. 在 return 中绑定到引用返回值的临时量在表达式末尾被销毁，这时会返回悬垂引用。好消息是从 C++26 开始会直接变成编译错误：

    const int& func(void) { return 0; }

  3. 还有 C++20 新增的一条匪夷所思左右脑互搏的规则：绑定到用圆括号初始化器 () 初始化的聚合体引用成员的临时量存在到该表达式末尾：

    struct foo { int&& r; };
foo bar{1};  // OK
foo bar(1);  // bar.r is dangling reference

    何意味 😅？生怕 UB 不够多是吧。

📌 重要

只有引用绑定才有这样延长生存期的功能，如果只是一般的临时量实质化是不会延长生命周期的， 上面数组右值的那个例子中的指针 p 是悬垂指针。

你以为这就结束了？Nonono，和我们伟大的模板结合之后又双叒叕有新的规则了。考虑下面这段代码：

void func(const std::string&);
void func(std::string&&);

如果我们要让一个函数参数能够同时接收不同值类别，最直接的方法就是像上面这样做。但这样的问题也非常明显：如果我有 $N$ 个函数参数， 那显然我需要 $2^N$ 个函数才能覆盖所有参数组合，这是不可接受的。

所以就整了个万能引用出来，可以与模板推导结合实现同一个参数可同时接收左值和右值：

template <typename T>
void func(T&&);

for (auto&& v: rg) {}

想要理解上面这坨东西是怎么工作的，需要先知道引用折叠规则：

通过模板，typedef 或 using 中的类型操作可以构成引用的引用，此时适用引用折叠规则：右值引用的右值引用折叠成右值引用， 所有其他组合均折叠成左值引用。

非常好记忆，只需要记住 T + && 和 T&& + && 这两种情况能够形成右值引用类型，其余的全部会变成左值引用类型即可。 而且需要注意只有上面这三种情况才能进行引用的拼接，不能手动写像 int&& && a = 1; 这样的东西出来。

有了这个规则之后万能引用的实现就会变得十分自然，以上面的 func 为例看看是如何实现接收任意值类别的：

实参推导出的 T形参类型
1 (prvalue)intint&&
std::move(1) (xvalue)intint&&
a (lvalue)int&int&

如果实参带有 cv 限定也是同理的，会在基础类型 T 中自动添加。这也是为什么 void func(auto&); 不行的原因，声明中的 & 就导致 根据引用折叠规则永远无法构成右值引用类型，同时也不会自动添加 const 变成只读左值引用，所以只能接收左值。

至于这个万能引用还有什么妙用就留到下面再讲了。

📝 备注

万能引用依赖于模板推导，因此下面的都不是万能引用：

void func(std::string&&);

template <typename T>
struct foo { void bar(T&&); };

万恶的 decltype

值类别和引用的混沌世界中怎么能够少了亲爱的 decltype 呢？我们的 C++ 还是太喜欢重载了，除了函数和运算符， 连关键字都是可以重载的 😁。说你呢 virtual

decltype 最大的问题在于语义上的混淆，其有两种完全不同的功能和语义，但它们无论是从形式上还是输出结果都几乎一模一样， 完全让人摸不着头脑 😵‍💫。

decltype 功能一：根据标识符得到其声明时的类型。

如果实参是没有括号的标识表达式或没有括号的类成员访问表达式，那么 decltype 产生该表达式指名的实体的类型。 如果没有这种实体或该实参指名了一组重载函数，那么程序非良构。

这是在说什么呢？就是说如果传给 decltype 的实参符合这几个要求，得到的类型就是该标识符声明时候的类型，声明的时候怎么写的在这里 就会得到完全一样的结果。比如：

int a{};
int& ra = a;
int&& rra = std::move(a);

decltype(a);       // 得到 int
decltype(ra);      // 得到 int&
decltype(rra);     // 得到 int&&

struct foo { int&& m = 1; };
const foo* bar;

decltype(bar->m);  // 得到 int&&

template <int N>
void func(void)
{
    decltype(N);   // 得到 int
}

上面为什么要强调不带括号呢？decltype 有两个语义，总得有个方法来进行区分。但如果现在希望获取的不是 a 这个标识符的类型， 而是其作为表达式时的类型和值类别呢？这个时候就直接加上括号将其作为表达式处理即可。

decltype 功能二：得到表达式的类型和值类别。

如果实参是类型为 T 的任何其他表达式，且

  • 如果表达式的值类别是亡值，则 decltype 产生 T&&；
  • 如果表达式的值类别是左值，则 decltype 产生 T&；
  • 如果表达式的值类别是纯右值，则 decltype 产生 T。

逆天设计又来了，由于值类别没有专门的标识方式，所以只能使用类型系统进行表达，虽然好像也没有什么更好的方法就是了。上面的规则已经 比较简明易懂了，过程无非就是先推导出基本类型后再根据值类别添加不同的引用。唯一可以说的一点是 decltype 的操作数是不求值表达式， 放在里面的表达式不会产生副作用。

int&& a = 1;
decltype((a));               // 得到 int&
decltype(1);                 // 得到 int
decltype(std::move(a));      // 得到 int&&
decltype(std::terminate());  // 得到 void

当然，decltype 的使用场景远远不止上面这些，考虑以下代码，能否发现其中的问题：

// decltype(auto)
decltype(auto) func1(int x) { return (x); }
decltype(auto) func2(int x) { return ++x; }
decltype(auto) func3(int a, int b) { return a >= b ? a : b; }

struct S { int m = 0; };
decltype(auto) func4(void) { return (S{}.m); }

// Requires clause
template <typename T, typename U>
auto add(T a, U b)
requires requires {
    { a + b } -> std::same_as<T>;
    { b } -> std::same_as<int>;
}
{
    return a + b;
}

其中 func1 ~ func3 均返回悬垂引用，func4 编译期报错，而使用 add(1, 2) 会不满足约束。 而究其原因就在于 decltype(auto) 及 requires 表达式中的「符合要求」都是自动对操作数应用 decltype。 什么意思呢？让我们逐个分析一下：

对于 func1 ~ func4 来说，实际上等价于以下代码：

decltype((x)) func1(int x) { return (x); }
decltype(++x) func2(int x) { return ++x; }
decltype(a >= b ? a : b) func3(int a, int b) { return a >= b ? a : b; }

struct S { int m = 0; };
decltype((S{}.m)) func4(void) { return (S{}.m); }

这里会直接用 return 后的表达式替换 decltype(auto) 的 auto 占位符，因此对于 func1 来说，是否添加括号对应的是两种不同的语义。 具体的推导类型如下：

函数名返回表达式值类别推导类型
func1左值int&
func2左值int&
func3左值int&
func4亡值int&&

由于均为引用绑定到局部变量或者临时量上，所以全部是悬垂引用。其实这几个例子并不是 decltype(auto) 的应用场景，其使用场景应该是 用于返回值的完美转发，像这样的普通情况使用 auto 的值语义就足够了。

而对于 requires 表达式中的复合语句来说，就相当于判断：

static_assert(std::same_as<decltype((a + b)), T>);
static_assert(std::same_as<decltype((b)), int>);

非常容易发现问题出在什么地方：decltype((b)) 得到的类型应该是 int& 而不是 int。对于复合要求来说，会将 {} 内的表达式直接 放入 decltype(()) 中。注意这里的两层括号，实际上是强制了 decltype 的功能二，将表达式的类型和值类别一起传入后面的约束中。

应用场景

那上面这叽里呱啦讲了一大堆的规则究竟有啥用呢？下面的几个场景基本就是促使 C++ 搞出这坨东西的原因。

移动语义

作为现代 C++ 中无人不知无人不晓最伟大的功能之一，呃，应该吧，其完善了 C++ 的对象模型与生命周期管理的语义，并通过语言规则强制 了某些优化，提升程序的性能。

如果你理解了前文的规则，就能够非常自然的知道移动语义是如何实现的。其本质上就是根据值类别选择更优的重载函数而已：

struct foo
{
    foo(void);
    foo(const foo&);
    foo(foo&&);
    ~foo();
};

foo a{};
foo b = std::move(a);

以上就是移动语义最典型的用法，即显式告诉编译器我们不再需要某个对象，可以将它的资源转移而不是拷贝给另一个对象。 以上面这段代码为例，使用 std::move 将 a 这个左值变为亡值表达式，然后重载决议选中 foo 的移动构造函数对 b 进行初始化， 并在移动构造函数中将 a 的资源给直接拿过来。而实际所有权的转移是写在构造函数中由程序员控制的，所以说 move 什么也没有移动。

从上我们也可以注意到右值引用类型的主要作用是作为函数参数，而不是像下面这样使用：

std::string str = "Hello";
std::string&& ref = std::move(str);

这毫无意义，因为 ref 和 str 是等价的。

📝 备注

C++ 标准并没有规定被移动后的对象处于什么状态、是否合法或者能否被访问，这个取决于具体的设计决策。 一般来说，至少对于标准库，访问被移动后的对象是安全的。

完美转发

既然右值配合上移动语义有这么多好处，那我们肯定不希望一个右值表达式传着传着就变成了左值。但偏偏右值引用类型的变量在使用时会 退化成左值。对于非泛型代码还可以手动进行 std::move 之类的操作，但如果是泛型代码呢？比如最最最经典的转发构造， 常见于各种容器实现：

template <typename T, typename... Args>
T* construct_at(T* location, Args&&... args)
{
    return ::new (location) T(/* 怎么填？*/);
}

在绑定到 args 的一堆表达式中很可能既有左值又有右值，如果直接将 args 参数包展开，则会让所有参数以左值转发给构造函数， 丧失优化机会。所以我们需要一种能根据原始值类别，自动的将 args 包中的每一个引用转换为原来的值类别的工具，也就是左值按左值转发， 右值按右值转发。而这就是 std::forward。

我们先来看看 std::forward 是怎么实现的：

template<typename T>
constexpr T&& forward(std::remove_reference_t<T>& t) noexcept
{
    return static_cast<T&&>(t);
}

template<typename T>
constexpr T&& forward(std::remove_reference_t<T>&& t) noexcept
{
    static_assert(!std::is_lvalue_reference_v<T>, "must not be used to convert an rvalue to an lvalue");
    return static_cast<T&&>(t);
}

可以看到，std::forward 有两个重载版本，它们之间唯一的不同就是一个接收左值而另一个接收右值。在上面这个「转发函数形参」的场景下， 显然只有第一个重载会被使用。同时需要注意的是这个函数的参数是不推导语境，无法从函数参数推导出模板参数，需要我们手动指定。 当直接填写类型 T 的时候会转换成亡值，按右值转发；而填写 T& 左值引用类型时会按照左值转发。

仔细想想。。。Ummm，怎么感觉不太对，我怎么知道每个参数要转发成什么类型？其实很简单，我们可以注意到填写 T 按照右值转发、 填写 T& 按照左值转发这个规则非常 “恰好” 的和万能引用模板参数推导规则对应上了：

绑定到函数的表达式类型和值类别推导出的模板参数需要在 forward 中填写的类型
std::string&&std::stringstd::string
std::string&std::string&std::string&
const int&const int&const int&
const int&&const intconst int

所以在上面的例子中，我们直接拿推导出的模板参数扔给 std::forward 就好了：

return ::new (location) T(std::forward<Args>(args)...);

正因如此，像 T&&, auto&& 这样的东西还有另一个名字叫做「转发引用」（不能有 const），专门和 std::forward 配合。

再来看看 std::forward 接收右值的重载版本，不难看出这玩意唯一的用处是将右值按照右值转发 😑。。。我实在是想不到会在什么场景下 使用这个重载，将一个右值转发为右值，std::forward 的核心价值是将退化成左值的表达式给提升回右值，将一个已知是右值的东西再转换 成右值还是太神人了，以至于连标准中给的例子都只使用了第一个重载版本。

除了函数参数会发生退化变成左值外，函数返回值也是另一个坑点，考虑这段代码：

auto invoke(auto&& func, auto&&... args)
{
    return std::forward<decltype(func)>(func)(std::forward<decltype(args)>(args)...);
}

注意 auto 类型推断单独出现的时候永远是值语义，不会自动变成引用语义，因此如果 func 返回一个只读左值引用，这里就会发生拷贝 而不是直接将该引用继续传递。所以我们希望的是将返回语句表达式中的类型和值类别作为该函数的返回类型，最直接的方式就是在函数末尾 加上一个使用 decltype 的尾随返回类型，然后把这个表达式在里面重新抄一遍。

当然，估计大伙都觉得一模一样的东西写两遍实在是糖丸了，所以在 C++14 中就整出了 decltype(auto) 这个东西来自动实现这个功能：

decltype(auto) invoke(auto&& func, auto&&... args);

decltype(auto) 其实还可以在声明语句中使用，也就是将初始化器放到 decltype 中，例如：

int i{};
decltype(auto) a = i;        // `a` is int
decltype(auto) b = (i);      // `b` is int&

但我基本找不到什么使用场景，也很少看见有人这样写，因此就不再展开了。

RVO

RVO (Return Value Optimization) 是一种将函数返回值直接构造在调用方栈帧上以消除返回值临时对象乃至于局部变量的优化技术， 是复制消除 (Copy Elision) 的一种。除了 RVO 外，C++ 中的复制消除规则还可以作用于异常对象和协程形参，在这里不会详细讨论。

一般来说，编译器优化会遵循「如同」原则，即一个正确的程序优化前后的可观测的副作用应当完全一致，但复制消除是为数不多的 可以不遵循这个原则的优化机制之一。因为其会消除掉中间对象及其构造和析构函数的调用，而其中的任何的副作用也会一起消失。

众所周知，RVO 分为 URVO (Unnamed) 匿名返回值优化，和 NRVO (Named) 具名返回值优化，下面分别进行介绍。

现在再说 URVO 其实已经不太准确，因为其在 C++17 中已由语言规则强制保证，不能再被称作是优化，而是可预测的标准行为。比如说：

struct foo
{
    foo(void) { std::println("Constructed"); }
    foo(const foo &) { std::println("Copied"); }
    foo(foo &&) noexcept { std::println("Moved"); }
    ~foo() { std::println("Destructed"); }
};

foo func(void) { return {}; }

int main(void) { auto a = foo(foo(func())); }

在 GCC16 下，以上代码只会进行一次构造和析构，不会有任何的中间对象。这和是否开启优化无关， 甚至 -fno-elide-constructors 这个 flag 也是不能阻止这个机制的：

Constructed
Destructed

而将 foo 类的拷贝和移动函数进行弃置也会得到一样的结果。究其原因，是 C++17 中的一项新规则： 非必须不会将纯右值实质化，并且它会被直接构造到其最终目标的存储中。 上面的 func 产生纯右值之后，这个「幽灵」被一直传递到 a 才发生实质化。

实践中只需要注意函数返回值必须是像上面这样的 prvalue，以及表达式的类型和函数返回类型要相同即可。

到了 NRVO 这边就要麻烦一点，标准没有也不太可能保证在哪些情况下会进行此类优化，但给出了可以进行这个优化的必要条件，我们要做的 就是尽可能不要违背这些条件，然后把剩下的交给编译器：

在返回类型是类类型的函数中的 return 语句中， 当操作数是（函数形参和处理块形参以外的）具有自动存储期的非 volatile 对象 obj 的名字时，可以省略结果对象的复制初始化， 改为将 obj 直接构造到函数调用的结果对象中。

这也是为什么下面这段代码是经典负优化的原因：

auto func(void)
{
    std::vector ret{1, 2, 3};
    return std::move(ret);
}

显然 std::move(ret) 并不是一个局部变量的名字，因此 NRVO 优化被禁用，必然会导致至少一次移动。

除此之外，还有以下场景会导致编译器无法进行 NRVO 优化：

  • 含有分支导致无法确定返回的对象：

    foo func1(int x)
{
    foo a{}, b{};
    if (x > 0)
        return a;
    else
        return b;
}

  • 形参与非自动存储期对象：

    foo func2(foo x) { return x; }

foo func3(void)
try
{
    throw foo{};
}
catch (foo e)
{
    return e;
}

foo func4(void)
{
    static foo a{};
    return a;
}

  • 类型不匹配：

    struct bar
{
    foo m;
    int n;
};

foo func5(void)
{
    bar a;
    return a.m;
}

    注意就算表达式 a.m 的类型是 foo，但由于编译器不可能将一个 bar 对象拆成两块来构造，因此依然无法进行优化。

事实上要做到 100% 的 NRVO 是不可能也是没有必要的，这玩意在大多数情况下应该都不会成为性能瓶颈， 如果非常在意的话可以在编译选项中添加 -Wnrvo 来查看所有标准允许但实际上没有进行优化的地方。

📝 备注

这个优化依然需要可用的复制或移动构造函数。原因就在于作为一个有移动资格的表达式，其本质上依然是一个泛左值， 在构造 “临时对象” 的时候必须要遵循语言规则，不能像传递纯右值那样省略构造函数。
